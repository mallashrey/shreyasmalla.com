Azure AKS CI/CD Pipeline

A multi-environment CI/CD project that tests and containerises a Node.js application, publishes commit-tagged Docker images, and deploys them to development and production environments in Azure Kubernetes Service.

View Source Code Back to Projects

Project Overview

This project demonstrates an end-to-end DevOps delivery process using GitHub Actions, Docker and Azure Kubernetes Service. The pipeline automatically validates application changes, builds a container image and deploys the application into separate Kubernetes namespaces.

Feature-branch changes are deployed to the development namespace. Changes merged into the main branch are eligible for deployment to the production namespace. Production deployment is protected through a GitHub Environment approval requirement.

Completed result: a working Node.js application running as multiple Kubernetes pods in Azure AKS and exposed through an NGINX Ingress Controller.

Architecture

Application changes travel through automated testing, image creation and Kubernetes deployment before being exposed through the public ingress endpoint.

CI/CD Pipeline

The GitHub Actions workflow separates continuous integration from environment deployment. Deployment jobs run only after the required testing and containerisation jobs complete successfully.

1. Unit testing

Executes the automated test suite across multiple supported Node.js versions using a build matrix.

2. Code coverage

Generates coverage information to confirm that application behaviour is validated before deployment.

3. Containerisation

Builds the Docker image and publishes versioned images using the Git commit SHA as the image tag.

4. Kubernetes deployment

Applies the Deployment, Service and Ingress manifests to the appropriate AKS namespace.

5. Environment protection

Uses a GitHub Environment approval gate before allowing deployment to production.

6. Integration testing

Sends a request to the deployed application health endpoint and verifies the returned status.

Deployment Environments

Git event Environment Kubernetes namespace Deployment behaviour
Push to feature/* Development development Automatically deploys and runs the development integration test.
Pull request to main Validation No production deployment Runs validation without deploying an unmerged change to production.
Push or merge to main Production production Waits for manual approval before deploying and testing production.

Manual production approval

The production job references a protected GitHub Environment. Even after the preceding jobs succeed, the deployment pauses until an authorised reviewer approves it. This reduces the risk of automatically releasing an unintended change.

Kubernetes Resources

Kubernetes manifests define the application Deployment, internal Service and external Ingress. Development and production use separate namespaces so that releases can be tested without replacing the production workload.

  • Deployment: manages the application pods, container image and replica count.
  • Service: provides a stable internal endpoint for the application pods on port 3000.
  • Ingress: routes incoming HTTP or HTTPS requests through the NGINX Ingress Controller.
  • Secret: supplies MongoDB credentials to the application without storing the password directly in the deployment manifest.
  • Namespaces: isolate development and production resources inside the same AKS cluster.

Deployment Verification

The container image deployed to production is tagged with the Git commit SHA. This connects the source revision processed by GitHub Actions to the exact container image running inside AKS.

GitHub commit Workflow run Docker image tag AKS deployment Running pods

This creates a traceable deployment record: the GitHub workflow processed a specific commit, published a matching image and deployed that version to the production namespace.

Deployed Application

The Solar System web application is exposed through the NGINX Ingress Controller. The page also displays the name of the pod that processed the request, providing visible confirmation that the response came from a Kubernetes workload.

Availability note: the AKS cluster may be stopped when it is not being demonstrated to reduce Azure costs. The screenshots, source code and deployment evidence remain available even when the live environment is offline.

Troubleshooting and Improvements

Missing Kubernetes namespaces

The initial deployment failed because the development namespace did not exist. The namespace was created before applying the application resources. 

kubectl create namespace development
kubectl create namespace production

Invalid ingress hostname

The ingress hostname initially contained an empty IP address, resulting in a hostname such as solar-system-development..nip.io. The workflow was updated to retrieve the external IP address from the NGINX controller before generating and applying the ingress manifest.

Missing job output

The integration-test job originally received a null ingress URL because the deployment job did not expose the step value as a job-level output. The workflow was corrected by assigning an ID to the step and mapping its value through the job’s outputs section.

Application readiness

An early integration test reached the ingress before the new pods were fully ready. The deployment process was improved by waiting for the Kubernetes rollout before testing the public endpoint. 

kubectl rollout status deployment/solar-system \
  --namespace production \
  --timeout=180s

Expired Kubernetes credentials

Azure Cloud Shell later returned an authentication error when querying the cluster. The AKS credentials were refreshed before running further kubectl commands. 

az aks get-credentials \
  --resource-group rg-solar-system-aks \
  --name aks-solar-system-dev \
  --admin \
  --overwrite-existing

Security Controls

  • Sensitive MongoDB passwords are stored as GitHub Secrets rather than committed to source control.
  • Kubernetes Secrets provide application credentials to the running containers.
  • Production deployment uses a protected GitHub Environment with manual approval.
  • Development and production workloads are separated using Kubernetes namespaces.
  • Docker images use immutable commit-based tags for deployment traceability.
  • GitHub Actions runs automated tests before any environment deployment begins.
